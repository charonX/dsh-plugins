# 0003: 副作用队列与领域存储选型

日期: 2026-11-13
状态: accepted
关联: ADR-0001（仓库外 bundle）, spec 0001 实现决策"持久化适配""副作用队列", ticket 02

## 背景

Dsh Manager 的对外动作（启动派工、向 Session 投递输入、Channel 写回）必须经过一个持久化的副作用队列：入队、重试、退避、幂等投递，DSH 中途崩溃后重启每个副作用只生效一次。开工前需要回答两个问题：

1. 领域状态放在 harness 的 storage-domain，还是独立的 SQLite 文件？
2. storage-domain 没有跨记录事务（README 明言 "The domain API has no multi-record transaction operation"），"取出一个待执行副作用并标记为执行中"以及"状态变更与新副作用一起写入"能否原子完成？

## 实测结论（ticket 01/02 期间）

storage-domain 的保证（`@deepseek-ai/dsh-storage-domain` README / 源码）：

- **单域单写链**：`put`/`update`/`delete` 全部排队执行，`update` 的 transform 在它的链槽内运行——并发 update 不交错。
- **单记录原子**：一条记录的一次写是原子的（后端先持久化，再改内存，再发事件）；后端拒绝则不发布变更。
- **无跨记录事务**：两条记录的"一起写入"必然是两次独立写，中间可以崩溃。
- **顺序变更事件**：`domain/changed` 按写链顺序逐笔发布（put 携带新快照），是通知不是事务参与者。
- **内存权威**：读同步来自内存，写后端先行；未知持久化结果要求关域重开。

## 决策

### 1. 领域状态用 harness storage-domain，不建独立 SQLite 文件

- 复用宿主已提供的 schema 校验、写链、变更事件、路由设施；独立 SQLite 文件要自建全部这些，且破坏"领域核心不感知底层存储"的端口设计。
- 写入量级是单人本地场景；确有高频点写需求时，用 storage-domain 的 `routes` 配置把本 bundle 的域路由到 `sqlite` 后端即可，领域代码零改动。
- 工单/副作用等记录是 JSON 文档形态，与域的 KV 文档模型同构。

### 2. 无事务的存活方式：单记录原子 + 恢复扫描 + 幂等键

- **取出并标记执行中** = 一条记录上的一次 `update`（pending → in-flight，attempts+1），单写链保证不交错，等效原子。
- **状态变更 + 新副作用**（如派工完成时写入工单状态并产生下链副作用）：按"新副作用先落库、状态后迁移"的顺序写两条记录；中间崩溃时，重启的恢复扫描按记录自身状态收敛，不存在"半事务"脏状态——副作用记录要么已存在（会被执行），要么不存在（上游状态未迁移，重走一遍）。
- **恰好一次的效果靠投递幂等**：崩溃后重启对 in-flight 记录重投（at-least-once），每个副作用携带稳定 `id` 作为幂等键，目标端按键去重后效果恰好一次。投递器契约里写明这一点。

### 3. 队列状态机

`pending →（取出）in-flight →（成功）done |（失败）pending[退避] |（超上限）failed`

- 重试退避：指数（默认 1s×4^n），超过尝试上限进入 `failed`——可查询，不静默丢弃。
- 调度器在每次状态迁移后为最近的到期记录排一个定时器；域变更事件驱动重算。
- 服务启动（`[Service.init]`）时执行 `recover()`：in-flight 重投、到期 pending 补排。

## 后果

- 正向：领域核心（纯状态机 + 端口）完全可内存测试；持久化是薄适配；换后端/加路由不动领域代码；看板订阅直接吃 `domain/changed`。
- 负面：目标端必须实现幂等去重（契约的一部分，不是可选优化）；无跨记录事务要求所有多记录流程按"先副作用后状态"排序并在评审时检查。
- 中性：`failed` 记录的清理与人工重放留给后续 ticket（工单跟单/补偿流程）。
