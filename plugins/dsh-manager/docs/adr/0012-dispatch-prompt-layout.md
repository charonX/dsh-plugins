# ADR 0012：派工提示词采用固定中文标题版式

- 状态：已采纳（2026-11-27）
- 相关：ADR 0011（派工提示词预算与指针单）——0011 定义"放什么"，本 ADR 定义"长什么样"

## 背景

ADR 0011 把提示词压缩到 3,774 → 937 字符量级之后，暴露了另一个问题：内容少了，但**仍然是一串平铺句子**。
真实快照里 11 个段落只有空行分隔，没有标题；骨架是英文（`Repo rules: read …`、`submit_report: progress / …`），
工单标题、完成门禁、人类发言是中文，两者混在同一行（`Ticket ticket-…: [external-agents] 实机验证 …（实现已合入 test）.`
甚至出现全角括号后跟英文句号）。

后果有两层：人看 `TicketDetail` 里的快照时要逐行判断"哪段是门禁、哪段是环境、哪段是工具契约"；
模型也缺少稳定的分节线索，容易把"约束"读成"建议"。而 ADR 0007 只定义了段落注册表、变量与锁定段，
从未定义渲染版式。

## 决策

1. **固定标题 + 固定顺序**：渲染时按 section id 归入固定标题，标题序列确定，顺序即语义顺序：
   工单行（无标题）→ `## 任务` → `## 上下文` → `## 流程` → `## 上游产出` → `## 人类回答` → `## 技能`
   → `## 环境` → `## 约束` → `## 返工要求` → `## 工具契约`。同一标题下的段落连续输出，不穿插。
2. **骨架用中文，内容保留原文**：标题、说明句、契约句属于骨架，用中文；工单标题、mandate、完成门禁、
   人类发言属于内容，**原样保留**（通常是中文），不翻译、不改写、不加句号——翻译会改语义，且看板快照必须
   与出单方原文逐字对得上。工具名、字段名、命令、路径保持原样：`submit_report`、`check_branch_rebase`、
   `repo=`、`mergeTarget=`。
3. **排版规则**：中文与英文占位符之间留空格（`按 <path> 的顺序执行`）；中文用全角标点，代码式枚举用半角
   斜杠与逗号（`progress / waiting / blocked / failed / not-needed / ready`）；标题不带编号——顺序固定后
   编号只会成为第二处需要同步的状态。
4. **section id 不变**：版式只改渲染，`DispatchPromptRecord.sections` 仍按 id 记录（`mandate`、`worktree`、
   `repoRules`、`report` …），预算归因、`TicketDetail` 段落展开与既有测试不受影响。
5. **单一渲染入口 + 结构测试**：新增 `renderSectionBlocks(sections)` 作为唯一渲染路径，
   `tests/unit/prompt-builder.spec.ts` 用一条用例锁定标题序列
   （`['## 任务', '## 环境', '## 约束', '## 工具契约']`）与 `工作树：`/`产出目录：`/`submit_report：` 的写法。

## 备选与否决

- **全英文骨架**：团队在中文语境下读快照会跳读中文内容，且英文句更啰嗦（样例 1,243 vs 937 字符）；
  工具契约用中文并不影响模型执行——工具名与参数仍是英文标识符。
- **XML 标签包裹每段**（`<task>…</task>`）：模型确实偏好显式分隔，但 Markdown 标题在快照里可读性更好、
  字符更少，且同一份文本要同时给人看。
- **中文标题带编号**（`## 1. 任务`）：编号与顺序重复，一旦插入新段就要全局重排。
- **保留英文骨架、只加标题**：仍是中英混排，问题只解决一半。

## 后果

- 样例工单提示词 1,243 → **937 字符**，同时获得可扫读的层次；段落 id 与预算统计完全不变。
- 文案即契约：15 个 boot spec 靠 `Ticket ticket-` 识别派工消息、靠 `Repo rules: read` 断言指针，
  改文案必须同步测试。本轮已统一改为 `工单 ticket-` 与 `仓库规则：动手前读`，并把这个易碎点记在
  `dispatch-prompt-budget.boot.spec.ts` 的过滤注释里。
- 内容段落的排版（中英文之间空格、全角标点）由出单方决定，渲染层不做二次改写——改写用户原文比排版不齐更糟。
