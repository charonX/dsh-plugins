# 第一版不做探测：兼容块从构建期快照推导

SPEC §5 计划用"候选矩阵 + 极小请求 + 记忆"确定网关方言（探测）。第一版不实现它：
兼容块改为在构建期由 `models.dev` 的 `reasoning_options` 形状推导，写进路由后由用户在
官方卡片内的编辑器里改或清除。原因是探测必须临时改写用户正在使用的配置（compat 只能
经 settings 文档生效，`prepareCall` 的 `configure` 只覆盖 reasoning/temperature/maxTokens），
代价是并发窗口、崩溃残留与 revision 抖动；而"能关掉思考"这个诉求里，真正稀缺的是
**哪类网关该写哪种方言**的知识，不是这台机器上的实测结果——快照已经能覆盖 OpenAI 兼容的那批，
未知网关退回官方自定义添加 + 手填兼容块即可。

## 考虑过的选项

- **带外探测**：不走适配器，直接用凭据打 `/chat/completions`，只把命中结果写一次配置。
  更安全，但要在插件里再养一份"候选 → 请求体"的映射，与 pi-ai 的发送逻辑构成第二个真相源。
- **临时别名路由**：`<route>#probe` 指向同一端点，真实路由不动。仍是写 settings，且假路由会
  出现在目录与模型选择器里，崩溃后还要清理。
- **只给建议 + 复制 YAML**：放弃写配置。退化成社区插件的形态，没有任何增量。

## 后果

- 写进配置的是**未验证的推测**，错了表现为 400 或思考关不掉。因此三条硬约束：
  不覆盖已有值、写入值为可撤销的显式值（`unset` 即回到自动探测）、界面标注来源与快照时间。
- 插件不需要 Host 侧能力（探测要的 `prepareCall`、凭据、回滚都不再需要），因此没有 HTTP 通道、
  没有自有 settings 命名空间，也没有 memory 配置面。
- 若将来重启探测，本文应被新 ADR 取代，且需要重新回答"临时写配置如何收敛"这一问题；
  `src/dialect.ts`（形状 → 候选 → 兼容块）可直接复用为探测的输入层。
